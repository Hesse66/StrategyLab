# Codex Design Workflow

This workflow exists because frontend redesign fails when Codex asks a design model for inspiration, then tries to reinterpret the result by hand. The design model must produce the literal frontend files that Codex will paste, adapt, test, and repair. Codex owns backend truth, contract extraction, reference generation, integration, debugging, and final documentation; the design model owns the first serious frontend implementation pass.

The core idea is this: do not ask Gemini, Opus, Stitch, or any other design model for a mock, concept, style guide, or inspirational HTML. Give it a complete backend handoff, two strong visual reference boards, the exact target file list, and a strict instruction to output the real files. Codex should not translate a mock into the app unless the user explicitly asks for that slower manual path.

## When To Use

Use this workflow when a project has working or specified backend behavior and needs a frontend created or replaced around that behavior. It applies to new backend-first apps, existing apps with weak or confusing frontends, local tools, dashboards, games, workflow products, CRUD apps, data products, AI products, and any domain where the frontend must express the product world rather than look like a generic template.

Avoid this workflow for a small component patch, a styling tweak, or a direct frontend bug fix. In those cases, Codex can edit the existing UI directly.

## Roles

Codex extracts the complete backend and product truth. It identifies every route, endpoint, state object, event handler, storage key, selector, form field, dynamic render path, test expectation, and edge state that the frontend must preserve. Codex also generates reference images, writes `agentic/design/ONLY-BACKEND.md`, sends that handoff to the design model, applies the returned literal files, runs the app, repairs integration seams, and only then writes the final design documentation.

Gemini, Opus, or the chosen design model designs and implements the real frontend files listed in the handoff. It must organize every page, mode, state, data object, and workflow from the backend brief into a coherent UX. It must not invent a separate prototype, bypass backend calls, remove required selectors, rename contracts casually, or output a static mock unless the user explicitly asked for one.

## Required Artifacts

Before the design model runs, Codex creates exactly one handoff document and reference images:

- `agentic/design/ONLY-BACKEND.md`
- `agentic/design/references/design-style.png`
- `agentic/design/references/design-system.png`
- Optional extra reference images only when a specific product surface genuinely needs them.

Do not create `DESIGN.md` before the frontend exists. The final `agentic/design/DESIGN.md` is written only after Codex has integrated and debugged the returned frontend, because the durable design system must describe the real working result rather than a hope or a mock.

## Phase 1: Extract The Backend Handoff

Codex must inspect the backend and current frontend contracts deeply enough that the design model receives the whole product, not just a vague app description. The handoff must show what data exists, how it changes, what the user can do, what each page must prove, what normal users should see, what debug/admin users may see, and which files the design model must create.

For an existing app, ignore the current visual design unless the user says a specific element should survive. Do preserve all working contracts: routes, selectors, IDs, handlers, component props, API calls, generated classes, test hooks, storage keys, file paths, and dynamic render semantics. If the existing frontend is ugly but wired correctly, extract its contracts; do not copy its hierarchy blindly.

The backend handoff must be much more detailed than a product summary. It should read like the handoff a senior product engineer would give a frontend architect: every page, every mode, every data table, every important field, every action, every loading/empty/error state, and every debug surface that needs to be organized into UX.

## Phase 2: Generate Reference Images

The reference images are not full app screenshots. Full screenshots can underrepresent the backend when the app has many pages, tables, forms, states, and workflows. Instead, generate two sophisticated reference boards that guide the design model across any product type.

`design-style.png` should communicate aesthetic stance. It is about the visual world: palette, typography voice, material texture, icon personality, atmosphere, density, contrast, shape language, motion mood, and what the product should feel like at a glance. It can look like a polished style board with color systems, type specimens, material swatches, surface examples, brand-world cues, and a few abstracted product fragments. It should not pretend to contain every backend field.

`design-system.png` should communicate implementation grammar. It is about UX and components: navigation models, page layout patterns, responsive behavior, tables, cards when appropriate, forms, buttons, inputs, tabs, sidebars, drawers, modals, status indicators, empty/loading/error states, focus states, destructive states, dense data displays, and hierarchy rules. It should feel like a robust open design system board in the spirit of Material Design-level completeness, but tailored to the product’s desired aesthetic rather than generic Material styling.

Use image generation prompts shaped like this:

```md
Create a high-fidelity design reference board for a frontend implementation model.

This is not a full app mock and not production code. It is a reference image that communicates the design direction the model should use when creating literal frontend files.

Product:
[PRODUCT SUMMARY]

Reference type:
[design-style OR design-system]

Backend and UX scope:
[SUMMARIZE THE MOST IMPORTANT DATA TYPES, PAGES, WORKFLOWS, AND STATES]

Design intent:
[UI LOOKS, UX FEELS, MATERIAL, DENSITY, TYPOGRAPHY, COLOR, MOTION]

Must show:
[FOR design-style: palette, typography, material surfaces, mood, visual signature]
[FOR design-system: nav, layout, tables, forms, buttons, inputs, states, responsive examples]

Avoid:
- Generic SaaS dashboards.
- Chat wrappers unless the product is actually chat.
- Purple gradient templates.
- Decorative glassmorphism without functional purpose.
- Full interface screenshots that omit most backend reality.
- Tiny unreadable text or impossible layouts.

Output:
- One polished reference board.
- No browser chrome.
- No annotations that contradict the backend.
- Clear enough that Gemini or Opus can implement a real frontend from it.
```

When the product has a highly specialized workflow that cannot be inferred from the two boards, add one focused workflow reference image. Treat that as optional and justify it in `ONLY-BACKEND.md`.

## Phase 3: Put The Design Model Prompt Inside ONLY-BACKEND.md

The handoff file itself must contain the prompt for Gemini or Opus. Do not create a separate prompt file. The user should be able to open `agentic/design/ONLY-BACKEND.md`, attach the reference images, paste the prompt section into Gemini/Opus, and receive literal files.

The prompt must require exact output. It should say which files to create, which file to output first, how to split across turns if the model has output limits, and that every response should contain copy-pasteable file contents rather than descriptions.

Use this prompt shape inside `ONLY-BACKEND.md`:

```md
# DESIGN MODEL PROMPT

You are designing and implementing the real frontend for this backend. This is not a mockup task. Produce literal files that Codex can paste into the repository.

Use the attached reference images:
- `design-style.png` for aesthetic direction.
- `design-system.png` for component, layout, and UX grammar.

Read the entire backend handoff above before writing code. Organize every listed page, data group, state, and flow into a coherent UX. Preserve every contract listed under Contracts To Preserve.

Exact files to output:
[LIST EXACT FILES]

Output rules:
- Output complete file contents, not snippets.
- Do not output a standalone demo.
- Do not output fake backend logic.
- Do not rename required IDs, selectors, routes, functions, storage keys, or data attributes unless the handoff explicitly permits it.
- Do not omit secondary/debug surfaces; place them in the right UX layer.
- Do not invent dependencies outside the stated budget.
- If output is too large, split by file in this order: [ORDER].
- At the top of each response, state which file(s) are included.

Quality gate:
The result succeeds only if Codex can paste the files into the listed paths, run the existing app, and see the real backend data and workflows rendered through the new design without hand-translating a mock.
```

This prompt should be specific to the project but universal in method. A trading app, game editor, medical intake system, CMS, CLI dashboard, CRM, or AI research tool should all receive the same level of backend inventory and exact file contract.

## Phase 4: Send To Gemini Or Opus

Use Gemini or Opus when possible for the literal frontend generation pass. The design model should receive:

- The full `agentic/design/ONLY-BACKEND.md`.
- `agentic/design/references/design-style.png`.
- `agentic/design/references/design-system.png`.
- Any optional workflow reference image listed in the handoff.

Ask it for literal file contents. If the app has several files or the model has tight output limits, request files in turns. Do not accept a response that only describes a design, gives partial snippets, or creates a separate prototype. Ask for a repair pass immediately when the output is not pasteable.

## Phase 5: Codex Integration And Debugging

After the user brings back the generated files, Codex integrates them into the real app. Codex should apply the files with scoped patches, preserve backend behavior, run syntax checks, run tests, start the app, and browser-smoke the real runtime. The design model’s files are allowed to be imperfect, but they must be the starting implementation, not a visual reference Codex reinterprets from scratch.

Codex must verify:

- The app loads with the real backend.
- Every required route, ID, data attribute, handler, storage key, and API call still works.
- Dynamic data renders in the intended surfaces.
- All primary flows can be completed.
- Empty, loading, error, debug, and destructive states are visible and styled.
- The page scrolls correctly.
- Fixed headers, rails, panels, and command bars do not hide content.
- Text does not overlap.
- Buttons and inputs keep stable dimensions.
- Mobile and desktop layouts are usable.
- Console errors are absent or understood.
- Tests pass or failures are explained with a concrete repair path.

Repair seams locally. Common seams include missing dynamic selectors, broken event handlers, fake data left behind, external dependencies that violate the budget, layouts that assume too little data, hidden overflow, omitted debug surfaces, broken artifact links, and tables/forms whose real content exceeds the mock.

## Phase 6: Create The Final DESIGN.md Only After Integration Works

Only after Codex has integrated, debugged, and verified the frontend should it create `agentic/design/DESIGN.md`. This file documents the final working design system so future features preserve the same aesthetic, UI behavior, and UX grammar.

The final `DESIGN.md` should describe what actually shipped. It should include design tokens, layout primitives, component rules, navigation patterns, data display rules, form/control rules, responsive behavior, accessibility rules, state handling, animation rules, and examples that reference the real files/classes/components in code. It should also include the reference images as historical design inputs, while making clear that the working code is the source of truth.

Do not write `DESIGN.md` from the initial design ambition. Write it from the integrated result after browser verification.

## Two Standard Paths

**New backend-first project.** Define or implement the backend first, keep the frontend minimal, extract `ONLY-BACKEND.md`, generate the two reference boards, ask Gemini/Opus for literal files, integrate in Codex, repair seams, verify, then write `DESIGN.md`.

**Existing app frontend replacement.** Inspect the app, list what works, extract backend and frontend contracts from the existing implementation, ignore weak current visuals unless continuity is required, create `ONLY-BACKEND.md`, generate style/system reference boards, ask Gemini/Opus for literal replacement files, integrate, test, repair, and only then document the final design system.

## Quality Gate

The workflow succeeds when the design model receives a complete backend handoff and returns literal files that Codex can paste into exact paths. The integrated app must preserve backend behavior, render real data, support every primary flow, keep debug/admin surfaces available but secondary, pass tests and browser smoke checks, and feel like a distinctive product rather than a generic dashboard or model playground. The final `DESIGN.md` exists only after that integration succeeds and accurately documents the working system.
